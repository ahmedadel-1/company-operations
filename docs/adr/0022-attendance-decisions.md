# ADR-0022: Attendance decisions (Phase 7)

Date: 2026-10-04 · Status: Accepted

## Context
Phase 7 delivers attendance (ROADMAP P7): geofenced check-in/check-out, shifts and assignments, late and early-leave detection, missing-checkout handling, consumption of approved request effects (leave, remote work, business missions, short permissions), corrections through the Phase 6 approval engine, privileged administrator corrections, employee/manager/HR views, export and coordinate retention. `PRD.md` §7.4 and §12, `DATA_MODEL.md` §7 and `SECURITY.md` §2, §9 describe the Phase 0 logical design. Decisions follow the priority order repository documents → earlier ADRs → master specification → existing implementation → safest production practice. Where this ADR differs from the Phase 0 logical model, this ADR applies; the physical schema is in `DATA_MODEL.md` "Phase 7 — Attendance".

## Decision

### Privacy boundary (no surveillance)
- Location is read **only** when the employee presses Check in or Check out, in the foreground, through one `getCurrentPosition` call. There is no `watchPosition`, background task, polling, route, ping or continuous tracking anywhere in the product, and no API accepts location outside those two actions.
- Remote work and business-mission days **do not request location at all** (geofence result `NOT_REQUIRED`): there is nothing to compare against, so collecting it would be data without purpose.
- Stored per event: rounded coordinates (5 decimal places ≈ 1.1 m; more precision is not evidence), accuracy (whole meters, rounded up), the matched work location, its radius and the accuracy threshold at that moment, the server-computed distance and result, server time, IP address and user agent (≤ 512 characters). Nothing else from the device. Coordinates are never sent in emails or notifications and never appear in exports.
- Coordinate retention is a per-organization policy (`ATTENDANCE_COORDINATES`): after the configured number of days a bounded worker pass sets latitude/longitude to NULL on old events, keeping the result, distance, accuracy, location and times. Without a policy coordinates are kept (no purge without an explicit decision, PRD §12-E). Events under review or tied to an open correction are skipped until resolved. Audit logs are never purged.

### Fraud boundary
- Browser geolocation can be spoofed (developer tools, emulators, mock-location apps) and has variable accuracy. The system **does not claim** fraud-proof attendance: the UI says what is captured and that location is not tamper-proof, and documentation repeats it. A geofence result is evidence for dispute resolution together with server time, IP address, user agent and the review trail — not proof.
- What the server does guarantee: the time is the server's; the distance is computed on the server (haversine) from the reported point and the stored location; the client never chooses the result, the time, the location id or the distance; low accuracy is never `INSIDE`; every event is append-only.

### Work locations (reuse)
- Phase 2 `work_locations` (types OFFICE / CUSTOMER_SITE / PROJECT_SITE / OTHER, lat/lng `numeric(9,6)`, radius 10–5000 m, active flag) are reused unchanged. Their audit entries now include before/after radius, coordinates and active state.
- **Eligible locations** for a check-in are computed on the server: every active OFFICE location of the organization, plus every active location linked (`project_locations`) to an ACTIVE project on which the employee holds an active membership. The client sends only its position; the server evaluates every eligible location and picks the nearest **inside** one (ties: smallest distance, then id), otherwise the nearest one for the record. A client-supplied location id is not part of the contract, so foreign, inactive, unlinked or forged ids cannot be used.

### Accuracy and missing-location policy
- `attendance_policies` (one row per organization, managed with `org.settings.manage`, privileged + fresh MFA, audited): `maxAccuracyMeters` (10–5000), `lowAccuracyAction` (`FLAG_FOR_REVIEW` baseline | `REJECT`), `missingLocationAction` (`REJECT` default | `FLAG_FOR_REVIEW`), `missingCheckoutAfterMinutes` (30–1440, default 240).
- **No code default is treated as accuracy policy** (SECURITY §9): until an administrator saves a policy, location-based check-ins answer `409 ATTENDANCE_NOT_CONFIGURED`. The settings screen suggests 100 m. The dev seed saves a policy for the demo organization.
- Result rules (pure engine): accuracy > threshold → `LOW_ACCURACY` (never `INSIDE`, even when the point is within the radius); otherwise distance ≤ radius → `INSIDE`, else `OUTSIDE`. `OUTSIDE` is always rejected (`422 ATTENDANCE_OUTSIDE_GEOFENCE`, with the distance to the nearest eligible location). `LOW_ACCURACY` with `REJECT` → `422 ATTENDANCE_LOW_ACCURACY`; with `FLAG_FOR_REVIEW` the event is accepted with `review_status = PENDING_REVIEW`.
- When the device reports permission denied / unavailable / timeout, the client sends that status instead of coordinates. With `missingLocationAction = REJECT` → `422 ATTENDANCE_LOCATION_REQUIRED`; with `FLAG_FOR_REVIEW` the event is accepted as `PERMISSION_DENIED` or `UNAVAILABLE` and `PENDING_REVIEW` — recorded as such, never silently accepted (SECURITY §9).
- Reviews (`POST /attendance/events/:id/review`): `attendance.admin` (ORG) or `attendance.team` in scope; never one's own events. A pending review can be decided once (ACCEPTED / REJECTED with a note); a database trigger allows exactly that transition and nothing else on the event. A rejected review marks the record for HR follow-up (it does not delete or rewrite evidence); the correction flow is the remedy.

### Time and dates
- The server clock is authoritative. Client timestamps are not accepted.
- The **attendance time zone** of an employee is the profile time zone, else the organization time zone. It is snapshotted on the record.
- A **work date** is a local calendar date in that zone. For a check-in it is decided by the active shift window: a check-in belongs to shift day *D* when it falls inside `[start(D) − 4h, end(D) + missingCheckoutAfterMinutes]`; for an overnight shift starting 22:00 a check-in at 01:00 belongs to the previous day. Without a shift, the work date is the local date of the check-in.
- Local wall times are converted to instants with a DST-safe resolver (the `compatible` disambiguation of TC39 Temporal): a time inside a spring-forward gap is shifted forward by the length of the gap (02:30 → 03:30); a time inside a fall-back overlap uses the earlier (first) occurrence. Tested for gaps, overlaps, midnight and overnight shifts.
- Future days are never marked absent. A stored record without presence is `ABSENT` only when its work date is in the past; on the current day it is `SCHEDULED` (the missing-checkout sweep turns it into `ABSENT` once the day is over). History and team views add a derived **day status** for days without a record: `UPCOMING` (future), `NOT_STARTED` (today, before the scheduled end), `OFF_DAY` (no shift that weekday), `NO_SCHEDULE` (no assignment), `ON_LEAVE` / `ON_MISSION` (approved effect), `ABSENT` (past scheduled day with nothing recorded).

### Shifts and assignments
- `shifts`: name (unique, case-insensitive), start/end local time (`HH:MM`, stored as minutes), `crosses_midnight` (CHECK: true exactly when end < start), late and early-leave grace (0–240 min), ISO weekdays, active flag, `version`. Shifts are deactivated, never deleted.
- `employee_shift_assignments`: profile, shift, `effective_from`, optional `effective_to` (inclusive). A **GiST exclusion constraint** (`btree_gist`) forbids overlapping assignments for one profile; the service reports `409 CONFLICT`. Assignments are ended (set `effective_to`), never deleted; a past start cannot be moved.
- Overnight shifts are stored as end < start (`crosses_midnight` true); start = end is rejected.
- **Snapshots**: the record copies the shift id, name, start/end, overnight flag, graces, time zone and scheduled start/end instants when it is created. Later shift or assignment edits never recompute existing records.

### Records, events and derivation
- `attendance_events` is the **append-only evidence log** (UPDATE/DELETE/TRUNCATE revoked from the runtime role and rejected by trigger, with two narrow exceptions: the one-time review decision and the retention function nulling coordinates). Kinds: `CHECK_IN`, `CHECK_OUT`, `ADJUSTED`, `ADJUSTMENT_REVERTED`, `SYSTEM_MISSING_CHECKOUT`, `EFFECT_APPLIED`, `EFFECT_REVOKED`.
- `attendance_records` (one per profile and work date, unique) is the **derived state**: the service recomputes it from the record's events, its shift snapshot and the active request effects for that date with one pure function (`deriveRecord`) inside the same transaction as each new event. It is never deleted. Rebuilding from events gives the same state.
- Status: `OPEN` (checked in), `COMPLETE`, `MISSING_CHECKOUT`, `EXCUSED` (full-day leave or mission without presence), `ABSENT` (past day, nothing recorded), `SCHEDULED` (current day, nothing recorded yet). Mode: `OFFICE`, `SITE`, `REMOTE`, `BUSINESS_MISSION`, `LEAVE`.
- Effect materialization creates records only for past and current dates (LEAVE and BUSINESS_MISSION as `EXCUSED`); REMOTE and SHORT_LEAVE effects only touch records that exist (presence). Views derive everything else from effects directly.
- **Idempotency**: every check-in/out needs an `Idempotency-Key` (UUID). The key is unique per organization on the event table; a replay by the same member with the same action returns the original result (200, no new event); the same key for a different action or member is `409`. Every attendance write for an employee (check-in/out, review, correction, effect materialization, shift assignment) runs under a transaction-scoped **advisory lock per organization and profile** (`lockAttendanceProfile`), and the record is created with `ON CONFLICT DO NOTHING`, so double taps and concurrent devices never create two check-ins; the replay check is repeated inside the lock. System events use deterministic keys (`effect:<id>:<applied|revoked>:<date>`, `missing:<recordId>`, `adjust:<adjustmentId>:<applied|reverted>`).
- State rules: one check-in and one check-out per work day (a second check-in is `409 ATTENDANCE_ALREADY_CHECKED_IN`; check-out without check-in `409 ATTENDANCE_NOT_CHECKED_IN`; after check-out `409 ATTENDANCE_ALREADY_CHECKED_OUT`); check-out is never before check-in (server time is monotonic per record; adjustments are validated). Employees must have an ACTIVE membership and an employee profile with employment ACTIVE (`409 ATTENDANCE_NOT_ELIGIBLE` otherwise). A full-day approved leave blocks check-in (`409 ATTENDANCE_ON_LEAVE`); the employee can cancel the leave or HR can correct.

### Late and early leave
- Late minutes = check-in − (scheduled start + late grace), floored at 0; early-leave minutes = (scheduled end − early grace) − check-out, floored at 0. Computed from the snapshot only. No shift → neither is computed.
- A **short permission** (approved `SHORT_LEAVE` effect) with a time window excuses lateness when the window starts at or before the scheduled start (lateness counts from the window end) and early leave when the window ends at or after the scheduled end (early leave counts to the window start). Without a window it excuses both for that date. Full-day LEAVE / REMOTE / BUSINESS_MISSION: remote and mission days are still late/early-evaluated when checked in (they work the shift); leave days are excused.
- Phase 6 extension (additive): `workflowEffectsSchema.attendance` accepts optional `fromTimeField` / `toTimeField` (required `time` fields, SHORT_LEAVE only, validated at publish); `request_effects` gains nullable `starts_at_minute` / `ends_at_minute` captured at approval.

### Consuming Phase 6 effects
- The only input is `request_effects` (trusted, tenant-bound, written at final approval, revocable once). Attendance never reads request form data.
- Check-in, views and derivation read effects **directly** (status RECORDED, requester's member id, date in range), so a check-in right after approval is already correct. The `requests` queue jobs (`request.effect.recorded` / `request.effect.revoked`, relayed from the outbox) then **materialize** the effect on past and current dates of the range (bounded to 62 days): they append `EFFECT_APPLIED` / `EFFECT_REVOKED` events with deterministic idempotency keys and re-derive each record. Re-delivery is harmless; an effect from another organization, an unknown effect or an unapproved request is rejected (`UnrecoverableError`). Future dates are derived when they arrive.
- Revocation (administrator cancellation of an approved request) re-derives the same dates without the effect; evidence of both stays in the log.

### Corrections (no second approval engine)
- An employee submits a correction for one past or current work date (at most 31 days back) with a reason (`FORGOT_CHECK_IN`, `FORGOT_CHECK_OUT`, `WRONG_LOCATION`, `SYSTEM_ISSUE`, `INCORRECT_TIME`), the corrected check-in and/or check-out (local `HH:MM`) and details. The attendance service validates it against the record (check-out after check-in, not in the future, overnight shift handling) and, in one transaction, creates an `attendance_adjustment_requests` row (requested and original values) **and a Phase 6 request** of the reserved, system-provisioned type `attendance_correction`, submitted immediately (approver: direct manager by default; HR can change the workflow like any other type).
- The reserved type is created on demand (and by the seed) with a fixed form contract (`workDate`, `reasonCode`, `checkIn`, `checkOut`, `details`) and `effects.attendance = { mode: CORRECTION, dateField: workDate }`. Publish validation enforces that contract for the reserved key, `CORRECTION` is allowed only there, the generic catalog and `POST /requests` never offer or accept it (404), and attendance is the only producer.
- On final approval the Phase 6 engine records a `CORRECTION` effect; the worker reads the **trusted adjustment row** (not the form) and appends an `ADJUSTED` event (requester, approver, reason, original and adjusted values, request reference), then re-derives the record. Revocation appends `ADJUSTMENT_REVERTED`. Original evidence is never changed. Adjustment status is derived from the request status plus `applied_at` / `reverted_at`.
- Deviation from SECURITY §2.4 ("`attendance.team` approves corrections"): approvals come from the workflow (direct manager by default), which is the managerial reach the matrix intended, and keeps one approval engine.
- **Administrator direct correction** (`attendance.admin`, privileged → fresh MFA): sets check-in/out for a record with a reason code and a mandatory note; appends `ADJUSTED` with the admin as actor; audited (`attendance.record.corrected`). Never edits or deletes events.

### Missing checkout
- `attendance.missing-checkout.sweep` (new `attendance` queue, every 15 minutes): per organization in a system tenant context, at most 500 OPEN records whose scheduled end (or local end of day without a shift) plus `missingCheckoutAfterMinutes` has passed; when the check-in itself came later than that end, the grace runs from the check-in (Phase 8 fix, ADR-0023: before it, a check-in after the deadline created a record that could not be checked out). Check-out uses the same deadline. Each gets one `SYSTEM_MISSING_CHECKOUT` event (key `missing:<recordId>`) and status `MISSING_CHECKOUT`. **No check-out time is invented**; worked minutes stay unknown. One in-app notification per record (dedupe key), no email. The employee fixes it with a correction.

### Views, scope and export
- `attendance.self`: own Today and history. `attendance.team` evaluated with the existing policy engine (`listScope` / `canAccessResource`): TEAM = reach team members, DEPARTMENT = employee's current department in reach, PROJECT = employees with an active membership on a project in reach, ORG = all. Filters are applied in SQL; out-of-scope ids are `404`.
- HR/admin view = the same list at ORG scope with review and correction actions. No payroll, wages or overtime pay.
- Export: `GET /attendance/export` (CSV, `attendance.team`), at most 62 days and 10 000 rows, scope-filtered, formula-injection-safe cells, no coordinates, audited (`attendance.exported`). Bounded synchronous export instead of a background job (sizes are small; a background export is a later option).

### Rate limits
- New per-user `attendance` bucket: 10/min (SECURITY §5 "check-in 10/min/user"). Idempotent replays count too, but a client retries at most a few times, so 10/min never blocks a legitimate retry.

### Retention
- New category `ATTENDANCE_COORDINATES` with action `NULL_COORDINATES` (CHECK pairs them; other categories keep `DELETE_ROWS`), minimum 30 days. Managed in the existing retention screen (`org.settings.manage`, fresh MFA, audited); applied by the existing maintenance purge through a bounded SECURITY DEFINER function `purge_attendance_coordinates` (≤ 5000 rows per call, transaction-local flag, skips pending reviews and records with an open correction). Records, results and audit logs are retained.

### Notifications
- Through the outbox only: missing checkout (in-app), correction decisions (Phase 6 request notifications), review decisions (in-app). Never coordinates.

### Delivery details (decided during implementation)
- **Shift administration** is `attendance.config` at ORG scope (HR administrators and organization administrators in the seed); the accuracy policy stays `org.settings.manage` (privileged, fresh MFA). Shift and assignment changes are audited (`attendance.shift.*`, `attendance.shift_assignment.*`) but do not need fresh MFA: they never touch recorded days.
- **Assignment dates**: a new assignment starts today or later (organization date); an assignment can be ended no earlier than yesterday and never before it starts, so past days keep the shift they were scheduled with. Overlaps are rejected by the service under the employee lock and by the GiST exclusion constraint.
- **Administrator corrections** may reach back 366 days (employees: 31). An administrator cannot correct their own attendance (`403`); the event key is `admin:<recordId>:<recordVersion>` together with the record version check, so a double submit cannot apply twice.
- **Correction form values**: request form option values are lowercase (`forgot_check_in`, …) like every other select option; the adjustment row and the API keep the canonical upper-case reason code. The reserved type is provisioned on the first correction (advisory lock, created once) and by the dev seed.
- **Client accuracy warning**: when the reported accuracy is worse than the policy maximum, the Today screen first explains it and offers "Try again" (one more single reading) or "Send this reading" (renamed from "Submit anyway" in the Phase 8 consistency review; the text attached to the button says the server still applies the policy, refusing the check-in or recording it for review, and never counts the reading as inside). Nothing is retried automatically; the idempotency key of an attempt is reused only after a network or server error, so a manual retry can never record twice.
- **Configuration**: `RATE_LIMIT_ATTENDANCE_PER_MINUTE` (default 10) and `ATTENDANCE_SWEEP_INTERVAL_MS` (default 900 000, 1–60 minutes).
- **Navigation**: on phones the bottom bar's second slot is Attendance for members with `attendance.self`; Employees moves to the More sheet (UI_UX.md §2).
- **Notifications**: missing checkout and review decisions are in-app only (outbox, dedupe keys, no coordinates); correction decisions use the Phase 6 request notifications (in-app and email without form contents).

## Consequences
- Attendance evidence is append-only and reproducible; derived state can be rebuilt.
- Organizations must save an accuracy policy before location check-ins work (explicit decision, no hidden default).
- The Phase 6 engine gains a reserved type and an additive effect window; generic request APIs are unchanged for other types.
